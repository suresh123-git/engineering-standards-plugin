# /changelog

## Purpose

Turn commit and PR history into a user-focused changelog entry and recommend the next semantic version. Edits only the changelog and never touches released sections.

## Expected Input

A range (`v1.2.0..HEAD`), `unreleased` (default: last tag to HEAD), or a target version to cut. If no tags exist, ask for the starting point or use the first commit.

## Project Context Discovery

Run a light pass of [project discovery](../../standards/global/project-discovery.md). Additionally:

- Check for an existing `CHANGELOG.md`/`HISTORY.md`/`docs/changelog` and its format; check release automation (release-please, semantic-release, changesets, towncrier) — if present, **follow it** and explain how the file is generated rather than hand-editing generated sections.
- `git tag --sort=-creatordate`, `git log <range> --no-merges --pretty=...`, merged PR titles/labels (`gh pr list --state merged` if available).
- Read commit conventions to parse types and breaking changes.

## Applicable Standards

- [Changelog standards](../../standards/documentation/changelog-and-releases.md), [conventional commits](../../standards/git/conventional-commits.md)
- [Branching and releases](../../standards/git/branching-and-releases.md) — SemVer, tagging

## Execution Steps

1. Determine the range and gather commits/PRs; drop merge noise, reverts-with-original, dependency bumps and CI-only changes without user impact.
2. Classify entries into **Added / Changed / Deprecated / Removed / Fixed / Security**; map conventional types (`feat`→Added, `fix`→Fixed, `perf`/`refactor` with user-visible effect→Changed, `BREAKING CHANGE`→flagged).
3. **Rewrite each entry for users/operators**: impact, not implementation ("Prevent duplicate invoices when payment webhooks are retried"). Merge related commits; link PR/issue numbers.
4. Highlight **breaking changes** and migration steps prominently; note required config/DB changes.
5. **Recommend version bump**: BREAKING → major, `feat` → minor, otherwise patch; state the evidence.
6. Insert into `## [Unreleased]` (or create a dated release section if a version is specified); update compare links at the bottom; keep published sections untouched.
7. Verify: no secrets/internal ticket jargon, dates ISO, links valid, formatting consistent with the existing file.

## Output Format

- The updated changelog section (shown) and file path edited
- **Version recommendation** with justification
- Items omitted (and why) and any commits needing author clarification

## Safety Constraints

- Edit the changelog file only. Do not tag, bump versions in manifests, push or publish releases unless explicitly asked.
- Never rewrite previously released entries; never fabricate changes not present in history.
- If the file is auto-generated by tooling, do not hand-edit it.

## Examples

```
/changelog
/changelog v1.4.0..HEAD
/changelog cut 2.0.0
```
